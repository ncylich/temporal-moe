# Handoff: temporal-MoE on Android (Samsung SM-S942U1)

Written 2026-07-23 after one full session. Everything here is re-examinable — if you think a
result is wrong, re-measure it. Several of my own conclusions were retracted during the
session and yours may be too. What you should *not* skip is Section 1: those are the
requirements that make a result mean anything, and most of the wasted effort in this
session came from violating one of them.

---

## 1. What the setup fundamentally has to do (the core requirement)

The paper's claim is about **temporal expert residency**: keep R of E experts resident,
stream the rest on demand, and show decode stays close to the all-resident ceiling while
using far less memory. To measure that on Android you need **three regimes on the same
device, same session, same thermal state**:

| regime | what must be true |
|---|---|
| **fully resident** | every expert in RAM; nothing faults; this is the ceiling |
| **fully streamed** | no experts resident; every expert use fetches from storage |
| **temporally resident** | exactly R of E resident; the rest fetched on use |

For any of these to be a *measurement* rather than a story, four things must hold:

1. **Residency must be controllable and verifiable, not assumed.** You must be able to say
   "expert 47 of layer 12 is not in memory" and prove it (`mincore`), and prove that using
   it costs a real storage read (`/proc/<pid>/io read_bytes` or `/proc/diskstats`).
2. **Bytes moved must be countable.** The CUDA side reports `copied_bytes_per_token`. The
   Android equivalent is bytes actually read from the block device. Report measured bytes,
   never intended bytes.
3. **Only expert residency may vary between regimes.** Attention, norm and embedding
   weights are touched every token and must stay resident in *all three*. If they get
   evicted too, you are measuring "stream everything", which is a different and much
   slower thing. I made this mistake — see §5.
4. **The comparison must be a ratio to a ceiling measured on this device in this session.**
   Never compare to the A6000/Mac numbers directly, and never across thermal states.

**The honest problem you are inheriting:** requirement 1 is only half-satisfied by the page
cache, and I do not think mmap can fully satisfy it. See §6 for the recommended fix.

## 3. Measured device constants (reuse these, they're stable)

| quantity | value | how measured |
|---|---|---|
| UFS sequential read, cold | **1.92 GB/s** | `pagecache_tool coldread` |
| page-cache sequential read | **9.8 GB/s** | `pagecache_tool read` |
| active expert weights per token | **513 MiB** | from quantized tensor sizes; same for both variants |
| **decode cap if experts stream from storage** | **3.75 tok/s** | 1.92 GB/s ÷ 513 MiB |
| all-resident decode ceiling (fine) | **29.84 tok/s** (spread 2.2%, n=3) | `--mmap 0`, cold start |
| all-resident decode ceiling (coarse) | **32.66 / 33.71 tok/s** | `--mmap 0` |
| max page-cache residency of a 6.5 GiB file | **~75%** | full read then `mincore` |

**The roofline is the most useful thing here.** Any decode above 3.75 tok/s means the
experts are *not* coming from storage that token. Use it to sanity-check every result. It
also means a "75% of ceiling while streaming" target is arithmetically impossible on this
device — if you are asked for that, the answer is that the target needs restating, not that
the measurement needs improving.

## 4. The most important mechanism we found: real eviction needs TWO calls

Verified on-device with `revoke_test` (source in `androidbench/revoke_test.cpp`), touching
one 216 KiB expert slice and watching `/proc/self/io read_bytes`:

| action | next touch reads from disk |
|---|---|
| `madvise(MADV_DONTNEED)` alone | **0 B** — PTEs zapped, page stays in page cache |
| `posix_fadvise(POSIX_FADV_DONTNEED)` alone, while mapped | **0 B** — refused, range is mapped |
| **`madvise` then `fadvise`, in that order** | **221,184 B = exactly the slice** |

So per-expert revocation *is* possible, at page granularity, with byte-exact accounting,
without root. But either call alone silently evicts nothing. **My residency controller used
`madvise` only for most of the session, so it was never actually evicting — every regime
number produced before this discovery is void.**

Related gotchas, all verified:
- `posix_madvise(POSIX_MADV_DONTNEED)` is a **documented no-op on Linux**. Must be
  `madvise(MADV_DONTNEED)`.
- `ulimit -l` is **64 KB**, so `mlock` cannot pin weights. Residency can be *revoked*
  reliably but not *guaranteed* — the kernel may reclaim anything at any time.
- `mincore` is the only trustworthy residency readout. Use it before and after everything.

## 5. What we ran, what stands, what was retracted

### Stands

- **Ceiling**: 29.84 tok/s decode / 43.0 prefill (fine), reproducible to 2.2% over 3 runs.
- **`--mmap 0` is the only reproducible fast configuration.** Across 5-6 runs decode never
  moved more than ~4%. Every mmap-based config is **bimodal**: identical settings gave 28.49
  and 2.32 tok/s 40 minutes apart; the default policy gave 30.01 and 6.84. Anonymous memory
  is not reclaimable; page cache is.
- **The default loader re-reads the model 2-4x per run** (12.7-28.7 GB against a 6.5 GiB
  model) because it mmaps into reclaimable page cache and the kernel keeps evicting it.
- **`MAP_POPULATE` makes "cold" runs warm.** llama.cpp pulls the whole file in during *load*,
  before the timed window. A cold-cache decode number from the default path is a warm
  measurement with extra steps.
- **Routing is degenerate on random weights**: decoding 16x more tokens moved 0.06% more
  unique bytes off storage (6197 → 6201 MiB). The working set is ~513 MiB *total*, not per
  token. This is the same problem the CUDA side has — see §6.
- **Correctness**: PPL identical to 4 dp (185405.9848) across default / mode-2 / `--no-mmap`.
- **Under memory pressure** (balloon), decode becomes bimodal with sd up to 83% of the mean;
  means are not a valid summary there.

### Retracted (do not cite these)

| claim | why it died |
|---|---|
| "mode 2 gives a 19x win" | measured at n=8 decode tokens; collapses at realistic lengths |
| "coarse granularity is stable" | 34.36, 34.25, then **22.98** on the third run |
| "`--mmap 0` reads exactly once" | held 4 of 5 runs; one run read 2.75x |
| "the three regimes measured 0.13/0.08/0.11 tok/s" | all used `-p 0` on a cold cache, so every regime was measuring the same ~6.5 GB cold-load cost divided by 8-16 tokens |
| "residency controller gives R-of-E control" | it used `madvise` only — see §4, it wasn't evicting |

### Two things I never explained

- One `--mmap 0` run read 18.5 GB with prefill collapsing to 6.9 tok/s. No mechanism found.
- Mode-2 runs without a preceding prefill take ~600-730 s regardless of token count. Storage,
  swap and direct reclaim were each measured and each ruled out (`pgsteal_direct` was 0).

## 6. Where I'd go next (but argue with it)

**The page-cache approach probably cannot satisfy requirement 1.** We can revoke reliably
(§4) but not retain, we don't control fault granularity or timing, there's no deterministic
fetch/compute overlap, and the kernel can swap things behind us. We are approximating a
memory manager by arguing with one.

**The direct analogue of the CUDA design is an explicit slot pool:**
- don't mmap the expert tensors at all
- allocate a fixed pool of R expert slots in anonymous memory
- `pread()` (optionally `O_DIRECT`) an expert into a slot on demand — this is
  `cudaMemcpyAsync`'s counterpart, and it makes bytes-per-token directly countable
- a background thread can prefetch the next expert to get the overlap the CUDA path gets
  from streams

That gives all three regimes exactly (R=0, R=k, R=E), removes the kernel from the decision,
and makes the numbers defensible. Cost is roughly 200-300 lines in the model loader plus a
hook where MoE experts are gathered.

**Second, and independent: the degenerate router has to be dealt with.** The A6000 solved
this by *not trusting the router* — `TEMPORAL_SWAP_PROB=p` drives swaps at a prescribed rate
(see `llamacpp-bench/README.md:100` and `temporal.cu:45`). Whatever residency mechanism you
build, drive the turnover at a prescribed rate rather than hoping random weights produce
realistic expert churn. I started this (`LLAMA_TEMPORAL_EVICT_HZ`) but it was built on the
broken single-call eviction.

**Worth reconsidering:** whether the fine variant is the right primary model. 6.5 GiB fits in
8.5 GiB usable, so the interesting regime only exists under artificial pressure. A larger
model, or a smaller device budget, would make the question real rather than synthetic.

## 7. Methodology gates (learned the hard way; keep them)

- **Gate on `scaling_max_freq`, not `Thermal Status`.** This device reported thermal status 0
  while clamping the prime cores from 4742 MHz to 2227 MHz. Sample the clock *during* the run
  and record the minimum. Every sustained run here sags to 37-47% of rated; that is normal,
  not a spoiled run, but all arms must be in the same state.
- **`-p 0` on a cold cache puts the entire model load inside the timed decode window.** Always
  run a prefill test first, or you are timing the loader.
- **Don't pre-warm the page cache before a populating loader** — the two fight and produce
  10x the variance. My `warm()` helper did this and invalidated all of Phase D.
- **n=1 and n=2 are not enough for any mmap-based configuration.** Three claims died on
  replication this session. If a result matters, run it 3+ times, interleaved.
- **Verify eviction, pinning, and cache state — never assume.** `mincore` after eviction,
  `Cpus_allowed_list` readback after `taskset`, hash the GGUF on-device after push.
- Battery >= 80% and on AC, or the SoC is power-limited (worth 15-45%).
- Full guardrail list with citations: `BENCHMARK_GATES.md` (43 items, M1-M43).
